# Plan: running YARG natively on ARM64

rockbandPi currently runs the official YARG Linux x86_64 release under Box64. This document covers what a native ARM64 build of YARG would take, what blocks it today, and the steps that improve performance in the meantime.

## Where things stand (October 2026)

| Fact | Detail |
|---|---|
| YARG engine | Unity 6000.3.5f2 (YARG v0.15.0) |
| YARG scripting backend | Mono on every desktop platform (only Android is configured differently) |
| Official builds | Windows x64, macOS Universal, Linux x86_64. No Linux ARM64 ([YARG#1269](https://github.com/YARC-Official/YARG/issues/1269), open, no maintainer response) |
| Unity Linux ARM64 support | **Dedicated server players only** (no graphics, no audio), IL2CPP, since 6000.3. Still server-only in 6000.4 and 6000.5. |
| Full Linux ARM64 player with graphics | Only through Unity's **Embedded Linux** platform, which needs an Embedded/Industry license from Unity |

The last two rows are the real blocker. A native ARM64 YARG needs a Unity build target that regular Unity Personal and Pro licenses don't offer for desktop Linux on ARM64. Nothing in YARG itself prevents it.

### Native libraries YARG ships

| Library | Used for | ARM64 Linux available? |
|---|---|---|
| `libbass`, `libbass_fx`, `libbassmix`, `libbassopus` | audio playback, mixing, effects | Yes, un4seen publishes aarch64 builds |
| `STB2CSharp` | image decoding (album art) | Build from source |
| `libsqlite3` | song cache / scores | Yes (Debian `libsqlite3-0`) |
| `libusb-1.0` | Xbox 360 wireless receiver | Yes (Debian `libusb-1.0-0`) |
| `libhidapi-hidraw` (system) | HID instruments | Yes (Debian `libhidapi-hidraw0`) |
| `libRtMidi` | MIDI instruments | Build from source, or Debian `librtmidi` |
| `discord_game_sdk` | Discord rich presence | **No.** Disable it on ARM64. |
| `lib_burst_generated` | Burst-compiled C# jobs | Generated by Unity per target; depends on Unity supporting the target |

None of these block a port. Only the Unity player itself does.

## Phases

**Results so far (2026-10-04):** with the IL2CPP build from Phase 2 and the tuning in [performance.md](performance.md), songs run at 60 FPS on a Pi 5, both solo and with a four-player band.

### Phase 0: measure under Box64

Before changing anything, record a baseline on the Pi so later phases can be compared.

- Turn on YARG's FPS counter (Settings > Graphics).
- Play the same song each time: one 4-player full band song (guitar, bass, drums, vocals) and one solo drum song.
- Record:
  - average FPS and the worst stutters
  - whether audio drifts from the highway
  - input lag after calibration
  - CPU load (`top` over SSH: the `YARG` process and total)
- Record the same numbers for `YARG_RENDERER=vulkan` and `opengl` in `/etc/rockband-kiosk/kiosk.conf`.

Write results into `docs/performance.md` with the YARG version, Box64 commit and settings used.

### Phase 1: tune what's there (no rebuild)

Cheap changes, each measured against Phase 0:

| Change | Where |
|---|---|
| Lower render resolution (720p instead of 1080p/4K), lower graphics quality, turn off venues and background video | YARG settings |
| Box64 dynarec options: `BOX64_DYNAREC_BIGBLOCK`, `STRONGMEM`, `CALLRET`, `SAFEFLAGS`; per-game rcfile entry for YARG | `rootfs/opt/rockband-kiosk/yarg-launch.sh` |
| Newer Box64 | bump `external/box64` |
| CPU governor `performance`, optional mild overclock with active cooling | `config.txt`, a systemd unit |
| PipeWire buffer size (quantum) for lower audio latency | PipeWire config in `rootfs/` |

### Phase 2: IL2CPP x86_64 build of YARG (still under Box64)

**Status (2026-10-04):** steps 1 to 3 are in place:
- `external/YARG` is pinned at v0.15.0
- `patches/YARG/0002` adds the build method and `link.xml`
- `scripts/build-yarg.sh` / `.ps1` run the build
- `YARG_SOURCE` switches the image between the release and the local build

Discord is turned off through the kiosk's `settings.json` (`DiscordRichPresence: Hide`) instead of a patch. `patches/YARG/0001` also fixes Vulkan's depth format on the Pi. Step 4 (testing) is still open.

The official build uses Mono. Under Box64, Mono's JIT generates x86_64 code at runtime, which Box64 then has to translate again, with two code generators stacked. An IL2CPP build is compiled ahead of time to native x86_64 code, so Box64 translates it once and caches it. This is the most promising speedup that doesn't depend on Unity adding ARM64 support. It's legal: YARG is LGPL-3.0, and Unity Personal can build IL2CPP Linux players.

Work:
1. Add YARG as a submodule (`external/YARG`, pinned to the release tag) with our changes in `patches/YARG/`:
   - set the Standalone scripting backend to IL2CPP
   - add a `link.xml` that preserves types used through reflection (settings serialization, Newtonsoft.Json, input layouts from PlasticBand and HIDrogen)
   - disable Discord rich presence (not needed in a kiosk)
2. Build headless with Unity 6000.3.5f2 and the Linux IL2CPP module, using the `unityci/editor` container images (GameCI). A Unity Personal license file is needed for activation. It stays on the builder's machine and is never committed.
3. Add a `scripts/build-yarg.sh` that produces a Linux x86_64 IL2CPP zip, and let `image/stage-rockband/03-yarg` take either the official release or that local zip (a `YARG_SOURCE=release|local` setting in `kiosk.conf`).
4. Test on a PC first (all modes, all instruments through rb-bridge), then on the Pi, and compare against Phase 0.

Risks:
- Code stripping or reflection problems that only show up at runtime. These need a `link.xml` and a full test pass.
- IL2CPP builds take much longer to compile.
- YARG's code may assume Mono in places. These would need small patches, which could go upstream.

### Phase 3: native ARM64 build

Two ways in. Both are outside this project's control today.

**A. Unity adds a desktop Linux ARM64 player.** This is the likely path, given that Unity already ships the ARM64 sysroot and server player. Track the Unity 6 release notes for "Linux Arm64" player support.
When it lands:
1. Build YARG for Linux ARM64 with IL2CPP: the same pipeline as Phase 2, with the target architecture changed.
2. Provide ARM64 native plugins, as listed in the table above:
   - BASS aarch64 libraries from un4seen
   - STB2CSharp built from source
   - system sqlite, libusb and hidapi
   - Discord removed
3. Ship it in the image instead of the x86_64 build. Drop Box64, the `kernel8.img` switch (the Pi's default 16K-page kernel works again) and the x86_64 hidapi copy in `03-yarg`.
4. Offer the patches and build changes upstream to YARG so official ARM64 builds become possible ([YARG#1269](https://github.com/YARC-Official/YARG/issues/1269)).

**B. Unity Embedded Linux.** This works today on paper, but needs a commercial Unity Embedded/Industry license. That doesn't suit a hobby project or an open-source build anyone can reproduce.

### Not worth pursuing

- Unity's ARM64 dedicated server player: it has no renderer or audio.
- Porting YARG to another engine: far beyond the scope of this project.

## Fallback hardware

If Phases 0 to 2 can't reach a stable frame rate with a full band, the same image design works on an x86_64 mini PC (Intel N100/N150 class) with no emulation at all:
- swap pi-gen for a Debian live-build image
- drop Box64 and `kernel8.img`
- keep everything else as it is: rb-bridge, the drivers, the kiosk session and the SONGS partition
